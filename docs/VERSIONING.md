# 版本与发布管理

本文记录当前版本整理方案及后续协作约定。执行任何发布步骤前，以远端实时状态和验收结果为准。

## 当前版本安排

`v0.4.0` 包含 Responses API 支持。既有预发布 `v0.4.0-pre.1` 指向旧提交 `7b82f4d`，后续修复不会改写该标签。正式发布以实际创建的标签和 Release 为准。

搜索后端改造计划从已合并的 `main` 创建 `feature/search-backends`，目标暂定 `v0.5.0`；文章质量改造使用独立分支和 PR。版本和范围以最终验收结果为准。

本地未跟踪的评估资料应在切换工作区时保留，是否纳入版本控制另行审查。

## 分支规范

- `main` 是已合入的集成主线；是否正式发布由验收与 Release 标记确认，不直接向 `main` 推送开发提交。
- 新分支从明确的基线创建，使用小写英文、数字和短横线，格式为 `<类型>/<简短主题>`。主题描述工作内容，不绑定模型、会话或预计版本。
- `feature/`：新功能，例如 `feature/search-backends`；`fix/`：问题修复，例如 `fix/rate-limit-race`；`refactor/`：不改变产品行为的重构；`docs/`：文档；`chore/`：工程与维护。
- 紧急生产问题使用 `hotfix/<主题>`，从对应正式发布标签或确定的修复基线创建；修复需合回主线。
- 一个 PR 聚焦一个可审查主题。并行任务使用独立分支及必要的独立 worktree；有依赖时写明基线与合并顺序，不覆盖其他工作区的未提交文件。
- 已存在的 `codex/feature-v0.4.0-responses-api` 及其 PR 保持原样，完成后再按实际情况清理分支；不为统一命名移动已发布标签或改写共享历史。

## 版本号与发布

- 正式标签采用 `vMAJOR.MINOR.PATCH`；版本号按数字顺序递增，例如 `v0.4.0`、`v0.4.1`、`v0.5.0`，不使用日期代替版本号。
- 当前 `0.x` 阶段：`MINOR` 用于新功能或可能影响兼容性的变更，`PATCH` 用于兼容的修复和维护。兼容性变更须在 PR 和 Release 说明中写清；达到稳定对外兼容承诺时再考虑 `1.0.0`。
- 后续新版本的预发布使用 `vX.Y.Z-alpha.N`、`vX.Y.Z-beta.N` 或 `vX.Y.Z-rc.N`，同阶段序号从 1 递增；发布候选标记为 prerelease。排序示例：`v0.5.0-alpha.1` < `v0.5.0-beta.1` < `v0.5.0-rc.1` < `v0.5.0`。
- 保留现有 `v0.4.0-pre.1` 标签和 Release，不回溯改名；若仍需该版本的预发布则延续 `v0.4.0-pre.2`、`pre.3`，但只包含 `0.4.0` 已确定范围。
- 标签只指向经过验收的发布提交；不移动、覆盖已发布标签，也不对未经验证的构建标记正式 Release。
- 发布前核对代码注册版本、插件元数据、README、更新日志和标签的一致性。预发布的代码版本展示须先确认 AstrBot 版本解析兼容性。
- 每个 Release 写清功能变化、升级注意事项、验证范围与已知问题；是否设为 GitHub Latest 与正式版或预发布状态一致。

## 交付职责

- 开发会话负责实现、测试和本地 commit；项目负责人负责审核、文档、远端、PR、标签和 Release。
- 提交信息使用 `feat:`、`fix:`、`refactor:`、`test:`、`docs:`、`chore:` 等前缀，正文按需要说明原因。
- PR 说明包含问题、行为变化、兼容性、测试结果和未验证事项；确认 CI 与人工验收后再合并。
- 不将 CI 通过等同于真实 AstrBot、QQ 适配器和第三方服务的集成验收；发布说明应区分已验证和未验证范围。
